# Manual Test Guide — M12.1.5

ChangeLog + sliding-window summarization. The model now sees a record of
*why* the current artifact looks the way it does, and long-running
sessions retain coherent chat context without unbounded prompt growth.

Run on branch `M12.1.5-changelog-and-summarized-context`.

## What changed

### ChangeLog (new)
- `Session.changeLog: ChangeLogEntry[]` — appended exactly once per
  confirmed cascade (in `confirmCascade`, after the user clicks Confirm).
  Never appended for cancelled / drifted / dismissed attempts.
- Surfaced into every Phase-2 step prompt (workflow_discovery,
  screen_extract, dummy_data) as `<change_history>`. The block contains
  one entry per change with the user's full description.
- Step prompts now treat `<change_history>` as a binding requirement:
  *"do not undo any prior change unless `<user_feedback>` explicitly
  contradicts it. A screen the user explicitly added in a past turn
  MUST be retained even if the new workflow map does not obviously
  demand it."*
- Cleared on rollback to phase1; saved into the suspended snapshot;
  restored on suspended-restore (alongside the slots).

### Sliding-window summarization (new)
- `Session.chatSummary: string` — rolling summary of pre-window chat.
- `Session.changeLogSummary: string` — rolling summary of pre-window
  change-log entries.
- Trigger: when either list grows past **110**, the oldest items above
  100 are folded into a one-paragraph summary via a small LLM call. The
  list is trimmed back to 100 verbatim. Subsequent compressions extend
  the same summary.
- Applied in:
  - `op-1-1-conversation` (Phase 1 follow-up turns)
  - `op-2-9-conversation` (Phase 2 review classifier)
  - All Phase 2 stage runners (workflow / screen / wireframe) for the
    change log.
- Summary surfaces as `<earlier_conversation_summary>` in chat-using
  prompts and as a `Summary of older changes:` line inside
  `<change_history>` for step prompts.
- Soft-fail: if the summarization LLM call fails, the path proceeds with
  the uncompressed window — no regression in behavior.

### Verbatim window expanded
- Phase 1 conversation used to keep last 5 turns; Phase 2 classifier
  used to keep last 6. Both now keep up to 100 user/assistant turns
  verbatim, with summarization handling overflow.

## Test 1 — ChangeLog persists prior intent across cascades

The exact scenario you reported:

1. New session → `simple todo app` → Done → walk to screen review.
2. At screen review: `Add a screen to group lists` → preview banner →
   Confirm → screen regenerates with the new screen (vN).
3. Open the session JSON. Confirm:
   - `changeLog` has one entry with description "Add a screen to group
     lists" (or similar) and `firstImpactStepId: "screen"`.
4. At screen review again: `Add a "share with friend" workflow` →
   Confirm. Cascade rewinds to workflow.
5. Open the session JSON. Confirm:
   - `changeLog` now has two entries (oldest first).
6. Approve at workflow review → screen regenerates.
7. **Expect**: the regenerated screen inventory still contains the
   `group-lists` screen verbatim. The new "share-with-friend" workflow
   gets supporting screens added.
8. Inspect the LLM call sent to `screen_extract` (you can put a
   `console.log` in `prd-builder.ts` `buildUserMessage` if needed):
   - `<change_history>` block contains both prior change descriptions.
   - `<existing_screens>` block contains the v(N) screen list including
     `group-lists`.

## Test 2 — Cancelled / drifted changes leave NO log entry

1. At any review, send a change that drift-FLAGs (e.g. "add a third-party
   sync feature" against a contract that excludes it).
2. The drift banner appears; no preview banner.
3. Open the session JSON. Confirm: `changeLog` has no new entry.
4. Send a COMPATIBLE change → preview banner appears → click **Cancel**.
5. Open the session JSON. Confirm: `changeLog` still has no new entry.

## Test 3 — Rollback clears the changeLog; restore replays it

1. Build up a few cascades so `changeLog.length >= 2`.
2. Roll back to Phase 1.
3. Open the session JSON. Confirm:
   - `changeLog` and `changeLogSummary` are gone from the live session.
   - `suspended.changeLog` carries the entries.
4. Click Done without editing the contract → restorePhase2 runs.
5. Open the session JSON. Confirm:
   - `changeLog` is restored.
   - `suspended` is gone.

If you instead edit the contract → validate → fresh Phase 2 generation.
The changeLog is empty (correct: new context, no prior intent to preserve).

## Test 4 — Chat summarization triggers past 110 messages

You can reach 110 quickly by spamming questions in Phase 1.

1. Send 110+ messages (any mix). The LLM produces real responses, so
   this takes a few minutes. Easier alternative: temporarily lower the
   threshold in `src/lib/context/window.ts` (`COMPRESS_THRESHOLD = 12`,
   `VERBATIM_KEEP = 10`) and reload, then retry with shorter sessions.
2. After the 11th message (in the lowered-threshold setup), the next LLM
   call triggers compression.
3. Open the session JSON. Confirm:
   - `chat.length === 10` (or `VERBATIM_KEEP`).
   - `chatSummary` contains a 1-3 paragraph summary of the older turns.
4. Send another message. Confirm the LLM still has coherent context —
   look at the chat panel for the response.
5. Inspect the system prompt sent to `phase1.conversation` (logging
   helper or network tab): contains both the verbatim window and the
   `<earlier_conversation_summary>` block.

## Test 5 — ChangeLog summarization

Similar shape: build up >110 cascade entries (impractical without
helper). Recommended: lower the threshold for testing. The change log
should compress with the same shape as chat.

## Test 6 — Soft-fail on summarization error

Set an invalid `OPENROUTER_API_KEY` (or use a model id that doesn't
exist) and trigger a compression. The summarization call fails; you get
a `console.warn` in the server log; the session proceeds with the
uncompressed window. No regression — the user-visible LLM call after
compression still succeeds.

## Known limitations

- The threshold is hard-coded at 100/110. Could be config later.
- Summarization is synchronous inside the LLM-using path; it adds one
  extra LLM call per compression cycle. With `concurrency: 1` and 5min
  TTL, this is fine.
- The `<change_history>` block is included in every step prompt —
  workflow_discovery and screen_extract definitely need it; the
  workflow_detail fanout doesn't currently consume it (each fanout call
  is per-stub, scope-limited). Consider extending later.
