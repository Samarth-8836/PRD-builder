# Manual Test Guide — M12.1

The cascade-preview gate. Every COMPATIBLE change request now pauses for
explicit Confirm/Cancel before the cascade runs.

Run on branch `M12.1-cascade-preview-gate`.

## What changed in M12.1

- **New SSE event `cascade_preview`** is emitted in place of running the
  cascade immediately. Carries a `CascadePreview` (first-impact step,
  affected slots, estimated work, where the cascade lands).
- **In-memory pending-preview store** (`src/lib/session-manager/preview-store.ts`)
  keyed by sessionId, 5-minute TTL, never persisted. Survives in the
  same Node process between the chat request and the confirm request.
- **New API route `/api/cascade/confirm`** with `action: "confirm" | "cancel"`.
  Confirm streams the cascade via SSE; cancel returns 204 + drops the
  plan server-side.
- **`CascadePreviewBanner`** renders above the chat input whenever there
  is a pending preview. Shows the change description, first-impact step
  label, affected slot labels, estimated work, and where the cascade
  lands. Confirm/Cancel buttons.
- **Rollback clears any pending preview** server-side (in-memory map).
  New chat messages clear it client-side.

## What stays unchanged

- Phase 1 conversation flow.
- Question-mode (non-change) review chat replies bypass the gate
  entirely — only COMPATIBLE classifications go through preview.
- DRIFT and FLAG classifications still surface as drift banners; no
  preview is emitted (cascade was never going to run).
- The cascade itself (`runPhase2Cascade`) is unchanged. Confirm just
  defers when it executes.

## Test 1 — Preview banner appears at any review state

1. New session → `I want to build a simple todo app` → Done → walk to
   `phase2_workflow_review`.
2. In chat: `add a "share with friend" workflow`.
3. Expect:
   - Assistant message with the change summary.
   - Drift banner does NOT appear (COMPATIBLE).
   - Preview banner appears below the chat with: change description,
     first impact = "Workflow Map", affected = "Workflow Map", estimated
     work, lands at "Review: workflow".
   - Chat textarea is disabled with "Confirm or cancel the pending
     change above to continue."

## Test 2 — Confirm runs the cascade

1. From Test 1's preview banner, click **Confirm**.
2. Expect: workflow stage runs, progress events tick, and the session
   ends back at `review:workflow` with the updated Workflow Map slot.
3. Banner disappears, chat is unblocked.

## Test 3 — Cancel keeps state unchanged

1. Trigger a preview (any review state, any change request).
2. Click **Cancel**.
3. Expect: banner disappears, chat unblocks, session state and slots are
   identical to before the message.
4. Send another change request — preview banner appears again with the
   new plan. (Confirms the in-memory store accepts a fresh plan after
   cancel.)

## Test 4 — Rollback drops a pending preview

1. Trigger a preview.
2. Click **Roll back to Phase 1** instead of Confirm/Cancel.
3. Expect: rollback succeeds, banner disappears, session lands at phase1.
4. Open a fresh tab on the same session — no preview banner should
   reappear (server-side store was cleared).

## Test 5 — TTL expiry

1. Trigger a preview.
2. Wait 5+ minutes (or shorten `TTL_MS` in `preview-store.ts` for a
   faster test, then revert).
3. Click **Confirm**.
4. Expect: error like `No pending cascade preview for session ...`. The
   plan was evicted from memory; user has to re-issue the change request.

## Test 6 — Each cascade flavor surfaces the right preview

Trigger each at wireframe review:

- `add a "share board" workflow` → first impact: Workflow Map.
- `add a settings screen` → first impact: Screen Inventory.
- `make sample task names shorter` → first impact: Sample Data.
- `change the home screen to a card layout` → first impact: Wireframe
  HTML, with `firstImpactItemId: home`.

Each preview's affected-slot list should reflect the rewind scope.
