# Manual Test Guide — M12.2

Iteration on a locked pipeline. The user can request changes after the
session reaches `complete`; pipelineVersion bumps on each successful
iteration; the export bundle's filename reflects the version.

Run on branch `M12.2-iterate-on-complete`.

## What changed

- **Chat is unblocked at `state.complete`**. The same classifier + drift
  + cascade-preview gate as a review-state change runs. The cascade
  re-runs the affected steps (using `<change_history>` and
  `<existing_*>` priors) and lands either back at `complete` (in-place
  patches) or at the appropriate review state (full rewinds).
- **`Session.pipelineVersion` (default 1)** tracks the locked-output
  version. Bumped on the next return-to-complete after an iteration.
  In-place patches that don't transition state bump immediately at the
  end of `confirmCascade`. Persisted in suspended snapshot; restored on
  suspended-restore.
- **`Session.pendingVersionBump` flag** tracks "an iteration started
  from complete and hasn't settled yet." Set in `confirmCascade` when
  state was complete; cleared on the bump (return-to-complete or
  in-place finish), and on rollback (no bump — the iteration was
  abandoned).
- **DocumentPanel header chip** shows `vN` next to "Document" when
  `pipelineVersion > 1`.
- **Export filename** includes `-v{N}` suffix when `pipelineVersion > 1`
  (e.g., `simple-todo-app-abcd1234-v2.zip`).
- **ChatPanel placeholder** at complete: "Pipeline locked. Request a
  change to iterate, or roll back to Phase 1 to revise the contract."
  Roll-back button stays visible.

## What stays unchanged

- Phase 1 conversation flow.
- Review-state cascades behave identically — they don't touch
  pipelineVersion (only iterations from `complete` do).
- ChangeLog appends on every confirmed cascade (same as M12.1.5).
- Drift FLAG / DRIFT and cancelled previews leave no chat record / no
  changeLog entry / no version bump.

## Verification (no LLM calls)

```bash
npm run typecheck       # clean
npm run test:pipeline   # 30/30 pass
npm run build           # production build succeeds
```

## Test 1 — In-place iteration (data-only) bumps version immediately

1. New session → `simple todo app` → walk to `complete` (Done →
   approve workflow → approve screen → approve wireframe → approve
   complete). Confirm header shows no version chip yet (`v1` is the
   default — not displayed because it's the initial state).
2. At complete: send `make the sample task names a bit shorter`.
3. Preview banner appears with `firstImpact: Sample Data` and
   `lands at Complete` (auto-gate). Confirm.
4. Cascade runs in-place (data swap); state stays `complete` throughout.
5. Expect:
   - Chat shows "Added X" + "Locked v2." progress note.
   - Header chip now shows `v2`.
   - `data/sessions/<id>.json` has `pipelineVersion: 2` and no
     `pendingVersionBump`.
6. Click Export → filename includes `-v2`.

## Test 2 — Full-rewind iteration bumps after final approve

1. From the v2 state, send `add a "share with friend" workflow`.
2. Preview shows first-impact: `Workflow Map`, lands at
   `Review: workflow`. Confirm.
3. Cascade rewinds workflow; user lands at `review:workflow`. Header
   chip still shows v2 (bump pending).
4. `data/sessions/<id>.json` confirms `pendingVersionBump: true`.
5. Approve through the stages: workflow → screen → wireframe →
   `Approve → Mark Complete`.
6. At the final approval, the state transitions to complete and
   pipelineVersion bumps to **v3**. Header chip updates. Progress note:
   "Locked v3. Click Export to download the bundle."
7. JSON: `pipelineVersion: 3`, no `pendingVersionBump`.

## Test 3 — Rollback abandons the iteration; version doesn't bump

1. From any locked version (e.g., v3), send a workflow change → confirm
   → land at `review:workflow`. (`pendingVersionBump: true`.)
2. Roll back to Phase 1. Edit the contract. Click Done.
3. Phase 2 regenerates from scratch (different contract path).
4. Walk to complete.
5. Expect: `pipelineVersion` is still 3 (the failed iteration didn't
   count). The fresh Phase 2 lock IS v3 — the counter is monotonic
   regardless of contract changes.
   - If you'd rather have it bump on the post-rollback re-lock, that's
     a different design decision; current behavior treats rollback as
     an abandonment.

## Test 4 — Restore from suspended snapshot preserves version

1. From any state with v ≥ 2, roll back to Phase 1. Click Done without
   editing the contract.
2. Restored Phase 2 should show the same pipelineVersion as before the
   rollback (header chip persists).
3. JSON: `pipelineVersion` matches the pre-rollback value.

## Test 5 — ChangeLog accumulates across iterations

After Test 1 + Test 2, the session JSON should have at least 2 entries
in `changeLog` (one per confirmed cascade). The `<change_history>` block
in subsequent step prompts will include both descriptions.

## Test 6 — Drift FLAG/DRIFT during iteration leaves no version bump

1. From a locked v ≥ 2 state, send a clearly out-of-scope change (e.g.
   "add multi-user collaboration" against a single-user contract).
2. Drift banner appears (FLAG or DRIFT). No preview.
3. JSON: `pipelineVersion` unchanged, no `pendingVersionBump`,
   `changeLog` unchanged.

## Known limitations (lifted in M12.3)

- No History panel listing changeLog entries with diff summaries.
- No per-version diff view between v1 and v2 etc.
